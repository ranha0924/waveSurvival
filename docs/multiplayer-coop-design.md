# Wave Survival — 협동(Co-op) 멀티플레이 설계 문서

> 상태: **설계(Design) 단계** — 아직 구현 코드는 포함하지 않음
> 대상: 현재의 싱글플레이 Canvas 레이캐스터 FPS를 2~4인 협동 생존으로 확장
> 작성 범위: 아키텍처 결정 / 네트워크 모델 / 기존 코드 변경점 / 프로토콜 / 단계별 구현 계획

---

## 1. 목표와 범위

### 1.1 무엇을 만드는가
- **2~4인 협동(Co-op)**: 여러 플레이어가 **같은 맵**에서 **같은 웨이브**를 함께 생존
- 적(enemy) 스폰·AI·웨이브 진행은 **모든 플레이어에게 동일하게** 보여야 함
- 한 명이 쏜 총·죽인 적·획득한 픽업이 다른 플레이어 화면에도 반영
- 점수는 (a) 개인 점수 + (b) 팀 합산 점수 둘 다 트래킹

### 1.2 이번 범위에서 명시적으로 "제외"하는 것
- PvP / 데스매치 (다른 설계)
- 매치메이킹·랭크 시스템 (방 코드 기반 단순 참여로 시작)
- 음성 채팅
- 안티치트(서버 검증 강화)는 v1 이후로 연기

### 1.3 성공 기준 (Definition of Done)
- 호스트가 방을 만들고 코드를 공유하면, 다른 사람이 참여해 **서로의 캐릭터가 맵에서 보이고 같이 적을 잡을 수 있다**
- 60fps 렌더는 유지하되, 네트워크 동기화는 15~30Hz로 동작
- 한 명이 끊겨도 나머지 게임이 죽지 않음 (graceful handling)

## 2. 현재 구조 요약 (출발점)

| 영역 | 현재 상태 | 멀티 관점 영향 |
|------|-----------|----------------|
| 상태 관리 | `main.js`의 전역 `game` 객체 하나가 단일 진실원천(single source of truth) | **그대로 활용 가능** — 호스트의 `game`을 권위 상태로 승격 |
| 게임 루프 | `requestAnimationFrame` 기반 update→render | update와 render를 분리해야 함 (아래 4.4) |
| 적 AI | `enemy.js`에서 각 클라이언트가 로컬 계산 | **반드시 권위화 필요** — 안 그러면 적 위치가 어긋남 |
| 입력 | `game.keys`, `mouseDown`, `Player.turn()` | 입력을 네트워크로 전송하는 계층 추가 |
| RNG | `random.js` mulberry32 시드 기반 (일일 모드) | **시드 공유로 결정론적 동기화에 활용** |
| 렌더 | 레이캐스터가 `game.enemies` 등 배열을 그림 | "원격 플레이어" 스프라이트 추가만 하면 됨 |
| 네트워킹 | 없음 (Firestore 리더보드만) | 통신 계층을 0부터 신설 |

핵심 관찰:
- **이미 전역 `game` 객체로 상태가 중앙집중**되어 있어, "이 상태를 누가 소유하느냐"만 정하면 멀티 전환의 골격이 잡힌다.
- **이미 시드 RNG가 있어** 웨이브 구성·업그레이드 카드를 결정론적으로 만들 수 있다 → 동기화 부담 감소.

## 3. 아키텍처 결정: 권위 서버(Authoritative) vs P2P

협동 FPS에서 가장 중요한 건 **"적과 웨이브를 누가 결정하느냐"**다. 세 가지 후보:

### 옵션 A — 전용 WebSocket 서버 (권위 서버) ✅ 추천
- 가벼운 Node + `ws` 서버가 **권위 상태**(적, 웨이브, 점수)를 소유
- 클라이언트는 입력만 보내고, 서버가 계산해 스냅샷을 브로드캐스트
- 장점: 동기화가 깔끔, 치팅 방어 용이, 끊김 처리 쉬움
- 단점: 서버를 띄워야 함(호스팅 필요)

### 옵션 B — WebRTC P2P (호스트가 권위)
- 한 클라이언트가 "호스트" 역할을 겸함, 시그널링 서버만 작게 필요
- 장점: 상시 서버 비용 거의 없음
- 단점: NAT 통과(STUN/TURN) 복잡, 호스트가 나가면 게임 종료, 호스트 PC 성능에 좌우

### 옵션 C — Firestore 폴링 (기존 Firebase 재활용)
- 장점: 새 인프라 0
- 단점: **실시간 FPS에 부적합** — 지연 100~300ms+, 쓰기 비용 폭증. **비추천**

### 결정
> **옵션 A(전용 WebSocket 권위 서버)를 v1으로 채택.**
> 단, 서버 호스팅이 부담스러우면 **"호스트-권위 + WebSocket 릴레이"** 형태로 동일 코드를 P2P처럼 운용 가능(아래 3.1). 클라이언트 코드는 두 경우 거의 동일하게 작성한다.

### 3.1 "서버 잘 모르겠음" 사용자를 위한 호스팅 현실 가이드

| 방법 | 월 비용 | 난이도 | 비고 |
|------|---------|--------|------|
| **Render / Railway / Fly.io 무료 티어** | $0~ | 낮음 | Node `ws` 서버 배포에 가장 쉬움. **추천 시작점** |
| **Glitch / Replit** | $0 | 매우 낮음 | 프로토타입용. 슬립(sleep) 있음 |
| 본인 VPS (예: $5 Lightsail) | ~$5 | 중간 | 완전 제어 |
| Cloudflare Durable Objects / PartyKit | $0~ | 중간 | 서버리스 WebSocket, 확장 쉬움 |

권장 경로: **로컬 Node 서버로 개발 → Render 무료 티어로 배포**. 서버 코드는 100~200줄 수준이라 운영 부담이 작다.

## 4. 네트워크 모델 (권위 서버 기준)

### 4.1 역할 분담

```
┌─────────────┐         입력(input)          ┌──────────────────┐
│  Client A   │ ───────────────────────────▶ │                  │
│ (player 1)  │ ◀─────────────────────────── │  Authoritative   │
└─────────────┘      스냅샷(snapshot)         │     Server       │
┌─────────────┐                              │                  │
│  Client B   │ ───────────────────────────▶ │  - 적 AI/스폰    │
│ (player 2)  │ ◀─────────────────────────── │  - 웨이브 진행   │
└─────────────┘                              │  - 충돌/데미지   │
                                             │  - 점수 집계     │
                                             └──────────────────┘
```

- **클라이언트가 소유(권위)하는 것**: 자기 플레이어의 위치·시점(이동은 클라 예측). 책임 분산 + 반응성 확보.
- **서버가 소유(권위)하는 것**: 적, 투사체, 웨이브 번호/큐, 픽업 스폰, 데미지 판정 결과, 점수.
- **타협**: 빠른 FPS 반응성을 위해 "내 이동은 클라가 즉시 적용(client-side prediction)", 적/판정은 서버가 결정.

### 4.2 틱 레이트
- 서버 시뮬레이션 틱: **20Hz** (50ms) — 적 AI·충돌 계산
- 스냅샷 브로드캐스트: **15~20Hz**
- 클라 렌더: **60fps 유지** (스냅샷 사이는 보간/interpolation)
- 클라 입력 전송: **30Hz** 또는 변경 시

### 4.3 동기화 전략: 스냅샷 + 보간
- 서버는 매 틱 **상태 스냅샷**(적·플레이어·투사체 위치)을 보냄
- 클라는 마지막 2개 스냅샷 사이를 **선형 보간**하여 부드럽게 렌더
- 원격 플레이어: **interpolation**(과거 100ms 버퍼)
- 내 플레이어: **prediction + reconciliation**(서버 보정 시 부드럽게 수정)

> 대안(단순화): 이 게임은 적 수가 많지 않고 맵이 작아서, **"서버가 모든 적/플레이어 위치를 통째로 보내고 클라는 보간만"** 하는 단순 스냅샷 모델로 시작해도 충분히 플레이 가능. delta 압축은 v2 최적화로 미룬다.

### 4.4 게임 루프 리팩터링 (클라이언트)
현재 `loop()`는 update와 render가 한 덩어리. 멀티에선 분리 필요:

```
loop(now):
  dt = ...
  if (MP.isMultiplayer):
    Net.sendInput(localInputState)      // 내 입력 전송
    MP.interpolateRemoteState(dt)       // 원격 적/플레이어 보간
    Player.predictLocal(myPlayer, dt)   // 내 이동만 로컬 예측
    // 적 AI / 웨이브 스폰 / 데미지 판정은 로컬에서 "실행하지 않음"
    //   → 서버 스냅샷을 game.enemies에 반영만
  else:
    // 기존 싱글플레이 경로 그대로
    runFullLocalSimulation(dt)
  render()                              // 렌더는 공통
```

핵심: **렌더러(raycaster)는 거의 손대지 않는다.** `game.enemies`/`game.players` 배열만 올바르게 채워지면 그림은 그대로 그려진다.

## 5. 기존 코드 변경 지점 (파일별)

> 원칙: **싱글플레이 경로를 깨지 않는다.** `game.multiplayer` 플래그로 분기.

### 5.1 신규 파일
| 파일 | 역할 |
|------|------|
| `js/net.js` | WebSocket 연결, 메시지 송수신, (재)연결 관리 |
| `js/multiplayer.js` | 멀티 상태 머신, 원격 플레이어 관리, 스냅샷 적용·보간 |
| `js/lobby.js` | 방 생성/참여 UI(방 코드), 닉네임, 시작 동기화 |
| `server/index.js` | Node 권위 서버 (방, 틱 루프, 적 AI, 브로드캐스트) |
| `server/sharedSim.js` | 클라/서버가 **공유**하는 결정론적 시뮬 로직(가능한 만큼) |

### 5.2 기존 파일 수정
| 파일 | 변경 내용 |
|------|-----------|
| `main.js` | `game.multiplayer` 플래그 도입, `loop()`를 5.4처럼 분기, 적 AI/웨이브 스폰을 MP일 때 건너뜀. `game.players[]` 배열 신설(자신+원격) |
| `player.js` | 입력→상태 변환을 "직렬화 가능한 입력 패킷"으로 추출(`Player.sampleInput`). `Player.applyRemote()` 추가 |
| `enemy.js` | `Enemies.update`의 AI 부분을 **서버에서도 import 가능하도록** 순수 함수로 분리(브라우저 전역 의존 제거). 핵심 작업 — 5.3 참고 |
| `raycaster.js` | 원격 플레이어를 스프라이트로 그리도록 `game.players`를 sprite 목록에 추가(소량) |
| `enemy.js`/`weapon.js` | 데미지 판정을 "서버가 호출하는 순수 함수"로 노출 |
| `ui.js` | 팀 점수/플레이어 목록/연결 상태 HUD 추가 |
| `leaderboard.js` | 팀 모드 점수 제출 분리(개인 vs 팀) |
| `random.js` | 서버·클라가 **같은 시드**를 쓰도록 방 생성 시 시드 합의 |

### 5.3 가장 큰 난관: 적 AI의 권위화
현재 `enemy.js`의 AI는 브라우저 전역(`GameMap`, `game.player`)에 의존. 서버(Node)에서도 돌리려면:
1. AI 로직을 **순수 함수**로 추출: `stepEnemy(enemy, dt, {map, players}) → newEnemyState`
2. `GameMap` 충돌 헬퍼를 브라우저/Node 양쪽에서 import 가능하게 모듈화
3. 이 공유 로직을 `server/sharedSim.js`에 두고 **서버가 권위 실행**, 클라는 실행하지 않음

> 이게 멀티 전환에서 **공수의 50%**를 차지하는 부분. 다만 한 번 분리하면 싱글플레이도 같은 코드를 쓰므로 동작이 100% 일치한다.

### 5.4 원격 플레이어 표현
- `game.players = [{ id, name, x, y, angle, hp, weapon, isLocal }]`
- 레이캐스터의 sprite 수집 단계에서 `isLocal === false`인 플레이어를 **빌보드 스프라이트**로 추가
- 간단히 시작: 기존 적 스프라이트 자산을 색만 바꿔 임시 플레이어 아바타로 사용 → 이후 전용 스프라이트 제작

## 6. 프로토콜 설계 (메시지 스키마)

JSON으로 시작(디버깅 쉬움) → v2에서 바이너리(MessagePack) 최적화.

### 6.1 클라이언트 → 서버
```jsonc
// 방 참여
{ "t": "join", "room": "ABCD", "name": "무당" }

// 입력 (30Hz)
{ "t": "input", "seq": 1234, "keys": {"w":1,"a":0,"s":0,"d":1},
  "angle": 1.57, "pitch": 0.1, "shoot": 1, "weapon": "shotgun", "reload": 0 }

// 업그레이드 카드 선택 (웨이브 클리어 후)
{ "t": "pick", "card": "damage_up" }

// 핑
{ "t": "ping", "ts": 169... }
```

### 6.2 서버 → 클라이언트
```jsonc
// 방 입장 확정 + 초기 동기화
{ "t": "welcome", "you": "p2", "seed": 20260603,
  "players": [...], "wave": 3 }

// 상태 스냅샷 (15~20Hz)
{ "t": "snap", "tick": 5821,
  "players": [{"id":"p1","x":21.2,"y":19.8,"a":1.1,"hp":80,"w":"pistol"}, ...],
  "enemies": [{"id":11,"type":"grunt","x":..,"y":..,"hp":18,"st":0}, ...],
  "proj":    [{"id":3,"x":..,"y":..}],
  "pickups": [{"id":7,"type":"med","x":..,"y":..}] }

// 이벤트 (총격, 죽음, 픽업, 굿판 등 — 단발성)
{ "t": "ev", "k": "kill", "enemy":11, "by":"p1", "head":true }
{ "t": "ev", "k": "gutpan", "player":"p1", "dur":8 }
{ "t": "ev", "k": "waveClear", "wave":3, "cards": ["damage_up","hp_up","pierce"] }

// 게임 오버 (전원 사망)
{ "t": "gameover", "wave":12, "teamScore": 45000, "perPlayer": {...} }
```

### 6.3 설계 메모
- **단발성 이벤트(ev)**는 효과음·파티클·배너 트리거용. 위치/지속 상태는 `snap`으로.
- 적·투사체는 **서버가 부여한 안정적 id**로 추적 → 클라가 생성/제거를 매칭.
- 패킷에 `seq`/`tick`을 넣어 보간·재정렬·지연측정에 사용.

## 7. 게임플레이 규칙의 멀티 적응

| 기능 | 싱글 | 협동 적응안 |
|------|------|-------------|
| 웨이브 진행 | 혼자 다 잡으면 다음 | **모든 적 처치 시** 다음. 적 HP·수를 인원수에 비례 스케일(예: ×(0.6 + 0.4·N)) |
| 업그레이드 카드 | 1명이 1장 | **각자 개인 카드** 선택(개인 빌드 유지). 전원 선택 완료 시 다음 웨이브 시작 |
| 굿판 모드 | 개인 콤보 | 개인 발동 유지 + (옵션) "팀 굿판" 보너스 검토 |
| 부활 | 사망=게임오버 | **다운→팀원이 살려주기(revive)** 도입 권장. 전원 다운 시 게임오버 |
| 점수 | 개인 | 개인 + 팀 합산 둘 다 표시, 리더보드는 팀/개인 분리 |
| 보스(5웨이브) | 1마리 | HP 인원 비례 스케일, 미니언 소환 수 증가 |
| 픽업 | 줍는 사람 | 줍는 사람 우선(서버 권위로 중복 획득 방지) |
| 시드/일일모드 | 개인 시드 | **방 시드 공유** → 결정론적 웨이브로 동기화 부담↓ |

권장 신규 메커닉: **다운/부활(downed/revive)**. 협동 생존 장르의 핵심 재미이자, "한 명 죽으면 끝"의 답답함을 해소.

## 8. 끊김·지연·에러 처리

- **클라 끊김**: 서버는 해당 플레이어를 grace period(예: 10초) 후 제거. 재접속 시 같은 방 복귀 허용.
- **서버 끊김(P2P 호스트 이탈)**: v1에선 게임 종료 안내. (호스트 마이그레이션은 후순위)
- **지연 보상**: 적 판정은 서버 권위라 일부 "쏜 것 같은데 안 맞음" 발생 가능 → v2에서 lag compensation(서버가 과거 시점으로 되감아 판정) 검토.
- **상태 폭주 방지**: 파티클·시각효과는 **로컬 전용**(네트워크 비전송). 굿판 부적 파티클 등은 `ev` 이벤트로 트리거만.

## 9. 단계별 구현 계획 (마일스톤)

### M0 — 리팩터링 토대 (코드 안 깨고 준비)
- `game.multiplayer` 플래그, `game.players[]` 배열 도입
- `Player.sampleInput()` / `Player.applyRemote()` 추출
- 적 AI를 순수 함수로 분리(`stepEnemy`), `GameMap` 헬퍼 모듈화
- ✅ 검증: **싱글플레이가 이전과 100% 동일하게 동작**

### M1 — 통신 골격 (프로토타입의 핵심)
- 최소 Node `ws` 서버: 방 1개, join, input echo, 20Hz 틱
- `net.js`/`multiplayer.js`: 연결, 입력 전송, 스냅샷 수신
- **두 브라우저에서 서로의 캐릭터가 맵에서 움직이는 게 보임** (적 없이)
- ✅ 검증: 로컬 두 탭에서 서로 이동 동기화

### M2 — 적/웨이브 권위화
- 서버가 `sharedSim`으로 적 스폰·AI·웨이브 진행
- 클라는 적을 스냅샷으로만 표시 + 보간
- 총격→서버 데미지 판정→kill 이벤트
- ✅ 검증: **두 명이 같이 적을 잡고 웨이브가 같이 넘어감**

### M3 — 게임 규칙 통합
- 개인 업그레이드 카드 동기화, 인원 비례 스케일링
- 다운/부활, 팀 점수, 굿판 이벤트 동기화
- 연결 상태/플레이어 목록 HUD

### M4 — 견고화 & 배포
- 재접속, 끊김 처리, 방 코드 로비 UI
- Render 무료 티어 배포, 실측 지연 튜닝
- (선택) 바이너리 직렬화, delta 압축

## 10. 리스크 & 권장 결정

| 리스크 | 영향 | 완화 |
|--------|------|------|
| 적 AI 권위화 공수 | 높음 | M0에서 순수함수 분리에 집중, 싱글과 코드 공유로 일치성 확보 |
| 서버 호스팅 미정 | 중간 | 로컬 개발 → Render 무료 티어, 코드는 호스팅 무관하게 작성 |
| 지연으로 인한 명중감 저하 | 중간 | 클라 예측 + v2 lag compensation |
| 스코프 크리프 | 높음 | M1(서로 보이기)/M2(같이 잡기)까지를 "최소 가치"로 못박기 |

### 최종 권장
1. **옵션 A(권위 WebSocket 서버) + 결정론적 시드 공유**로 진행
2. **M0~M2를 1차 목표**로 (여기까지면 "협동 플레이"가 실제로 성립)
3. 호스팅은 **로컬 Node → Render 무료 티어**
4. 협동 재미를 위해 **다운/부활 메커닉**을 M3에 포함
